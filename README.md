# Hotel KPI Pipeline

A small Python pipeline that takes daily room data, cleans it, computes hotel KPIs
(occupancy, ADR, RevPAR), flags unusual days, and loads the result into SQLite
for SQL analysis.

The data is **synthetic**, generated by the project itself, so the pipeline can run
without any real hotel records.

## Pipeline

```
CSV ──► ReservationCleaner ──► add_kpis ──► flag_anomalies ──► SqliteLoader ──► SQL queries
        (validate, dedupe)     (occupancy,   (robust z-score    (daily_kpis      (sql/kpi_queries.sql)
                                ADR, RevPAR)  per room type)      table)
```

| Module | Responsibility |
|---|---|
| `transform.py` | Validation, KPI calculation, anomaly detection |
| `load.py` | Writes the table to SQLite and runs queries |
| `pipeline.py` | `KpiPipeline` ties the steps together and returns a run summary |
| `synthetic.py` | Generates sample daily data with a few injected errors |
| `cli.py` | `generate` and `run` commands |

## Run it

```bash
pip install -r requirements.txt
set PYTHONPATH=src
python -m hotel_kpi generate --out data/raw/daily_rooms.csv --days 365
python -m hotel_kpi run --source data/raw/daily_rooms.csv --db data/warehouse/hotel.db
python -m unittest discover -s tests
```

On PowerShell, use `$env:PYTHONPATH="src"` instead of `set PYTHONPATH=src`.

## Design decisions

**Robust anomaly score.** The first version used the trailing mean and standard
deviation. A single spike inflated the standard deviation, which hid a real zero-revenue
day right after it. A test caught this. The current version uses the trailing median
and MAD (median absolute deviation), which are not moved much by one extreme value.

**Threshold choice.** The threshold is 4 MAD units. I compared thresholds on the
synthetic data, using as approximate ground truth any day whose RevPAR is at most 20% or at least
250% of its room type's median. These labels are my own heuristic, not exact.

| Threshold | Flagged | True positives | Precision | Recall |
|---|---|---|---|---|
| 3 | 47 | 8 | 0.17 | 1.00 |
| **4 (default)** | **24** | **8** | **0.33** | **1.00** |
| 5 | 14 | 7 | 0.50 | 0.88 |
| 6 | 11 | 6 | 0.55 | 0.75 |

Threshold 4 catches every likely error, at the cost of more false alarms.
Threshold 5 has fewer false alarms but misses one. The right choice depends on
whether missing an error or reviewing extra days costs more for the business.

**Validation before loading.** Rows are rejected when the date is invalid, revenue is
negative, rooms sold exceed rooms available, or the key `(date, room_type)` is
duplicated. The run summary reports how many rows were rejected.

## Tests

Seven `unittest` tests cover cleaning rules, KPI formulas, anomaly detection (spike,
drop, and the no-history case), and an end-to-end run that writes to SQLite.

## Limitations

- Data is synthetic. Results show the method works, not real business performance.
- SQLite is used for simplicity. A production version would use PostgreSQL.
- The pipeline runs on demand. Scheduling (cron, Task Scheduler, or Airflow) is not included.
- The anomaly threshold was tuned on this synthetic data and would need checking against real data.

## Possible next steps

- Containerise with Docker and move the loader to PostgreSQL.
- Compare each day against the same weekday, to reduce false alarms on weekends.
- Add a scheduled run and log rejected rows to a separate table.
